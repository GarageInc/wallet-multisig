# Wallet Multisig: устройство MPC-кошелька и подготовка к собеседованию

В репозитории реализован кошелёк с распределённой генерацией ключа и пороговой ECDSA-подписью. Участники совместно получают общий публичный ключ, хранят разные секретные доли и выпускают **одну обычную ECDSA-подпись**, которую проверяет блокчейн.

Этот документ описывает исходный код коммита `0d6d40d9c1a8e6013a5337c3f7c4f4426332195f` от 30 июля 2024 года. Он включает объяснение алгоритма, разбор хранения секретов, обнаруженные проблемы и вопросы для собеседования.

**В этой версии обнаружены существенные дефекты безопасности и работоспособности.** Гарантии корректного порогового протокола нельзя автоматически переносить на эту реализацию. Математический пример «2 из 3» ниже объясняет задуманный алгоритм; успешный сквозной запуск такого кошелька не подтверждён. В частности, существующая проверка Paillier-модулей мешает генерации с тремя различными модулями.

## Архитектура

| Каталог | Назначение |
| --- | --- |
| [`whcypher_app`](whcypher_app/README.md) | Браузерное расширение: интерфейс, seed-фразы, криптография, локальное хранение долей |
| [`whcypher_api`](whcypher_api/README.md) | Express + MongoDB: сессии генерации, обмен сообщениями, сессии подписи, зашифрованные резервные копии |
| [`chain-service`](chain-service/README.md) | Адаптеры блокчейнов: адреса, транзакции, хеши, проверка подписей и отправка |

Новые кошельки используют `secp256k1-v2`. Выбор версии находится в [`MultisigSession.initSession`](whcypher_app/src/serviceWorker/app/models/MultisigSession.ts#L28). В репозитории также сохранена предыдущая версия протокола.

Краткое описание для собеседования:

> Это некастодиальный кошелёк с распределённой генерацией ключа и пороговой подписью. Общий приватный ключ математически существует, но штатный протокол не собирает его целиком. Каждый участник хранит собственную долю. Для создания кошелька участвуют все n участников, для подписи достаточно выбранных t. Сервер координирует обмен сообщениями, а блокчейн проверяет одну стандартную подпись.

Это описание архитектурной цели. Реализационные ограничения и ошибки разобраны отдельно ниже.

## Основные понятия

Для схемы «2 из 3»:

- `n = 3` — общее число участников;
- `t = 2` — минимальное число участников для подписи;
- `G` — базовая точка кривой secp256k1;
- `q` в формулах ниже — порядок группы кривой;
- все скалярные вычисления в этих формулах выполняются по модулю `q`.

Приложение допускает `2 ≤ t ≤ n ≤ 16`.

| Секрет или параметр | Значение |
| --- | --- |
| Seed-фраза | Корневой секрет конкретного пользователя |
| `u_i` | Личный вклад участника в общий ключ, выведенный из его seed по пути кошелька |
| `x_i` | Итоговая пороговая доля после обмена с другими участниками |
| `x` | Общий приватный ключ, который штатно целиком не собирается |
| `Y_i = u_i · G` | Публичный вклад отдельного участника |
| `Y = x · G` | Общий публичный ключ |
| Пароль расширения | Пароль для защиты локального хранилища; не общий ключ кошелька |
| Ключи Paillier | Вспомогательные ключи для распределённых вычислений при подписи |

Seed, исходный вклад `u_i` и итоговая доля `x_i` — разные сущности. Пароль пользователя, nonce подписи и nonce блокчейн-транзакции также нельзя смешивать.

## Генерация общего кошелька

Рассмотрим Алису, Бориса и Виктора, создающих кошелёк «2 из 3».

### 1. Каждый участник создаёт собственный seed

Приложение вызывает `generateMnemonic(160)`: это 160 бит исходной энтропии и 15 слов BIP39. Из мнемоники получается seed, из seed через HD-деривацию — дерево ключей.

Seed-фразы между участниками не передаются.

В интерфейсе создания и присоединения выбирается путь вида:

```text
m/44'/0/<случайный индекс>/<случайный индекс>
```

Личный секретный вклад `u_i` выводится из seed по выбранному пути. Путь сохраняется в данных кошелька и нужен при восстановлении.

Код: [`AppController.generateNewSeed`](whcypher_app/src/serviceWorker/app/controllers/AppController.ts#L108), [`Key`](whcypher_app/src/serviceWorker/app/models/Key.ts#L13), [`InitMultisigSession`](whcypher_app/src/app/pages/InitMultisigSession/InitMultisigSession.tsx#L54).

### 2. Инициатор создаёт серверную сессию

Клиент отправляет параметры:

```text
blockchain
minimumSigAmount = 2
partiesAmount = 3
protocolVersion = secp256k1-v2
expiresIn = 300000
```

Сервер создаёт запись `Vault`, возвращает `sessionId` и назначает инициатору `partyId = 1`. Остальные присоединяются и получают свои номера.

Номера участников используются как координаты в схеме разделения секрета. Они должны быть уникальными и согласованными между всеми сторонами.

Клиент ждёт подключения **всех `n` участников**, хотя для будущих подписей нужны только `t`.

Код: [`MultisigSession`](whcypher_app/src/serviceWorker/app/models/MultisigSession.ts#L194), [`TsWalletShard.initSession`](whcypher_app/src/serviceWorker/app/lib/TsWalletShard.ts#L122), [серверный обработчик](whcypher_api/src/controllers/vault_controller.js#L39).

### 3. Каждый создаёт публичный вклад и ключи Paillier

Из собственного seed по пути кошелька выводится `u_i`. Затем вычисляется:

```text
Y_i = u_i · G
```

Каждый участник также генерирует собственную пару ключей Paillier с модулем 2048 бит. Публичные ключи потребуются другим участникам при последующем создании пороговой ECDSA-подписи.

Код: [`generateThresholdKeyShare`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/handlers/VaultSessionHandler.ts#L19).

### 4. Обмен публичными данными и доказательствами

В первых сообщениях передаются:

- публичный вклад `Y_i`;
- commitment — криптографическое обязательство относительно этого вклада;
- данные раскрытия commitment;
- публичный ключ Paillier;
- доказательство корректности ключа Paillier.

Задача commitment — зафиксировать выбор до раскрытия данных остальных участников. Для такой защиты нужен порядок «сначала все зафиксировали, затем все раскрыли».

**Здесь commitment и раскрытие отправляются одним сообщением.** Полноценное разделение этих фаз в данном месте отсутствует.

Код: [`getRound1n2BroadcastMessage`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L115).

### 5. Каждый распределяет собственный вклад по схеме Shamir

Для порога `t = 2` каждый участник создаёт случайный полином первой степени:

```text
f_A(z) = u_A + a_A · z
f_B(z) = u_B + a_B · z
f_C(z) = u_C + a_C · z
```

Алиса вычисляет `f_A(1)`, `f_A(2)`, `f_A(3)`: часть для себя оставляет, части для Бориса и Виктора отправляет им. Остальные делают то же самое со своими полиномами.

При общем пороге `t` степень полинома равна `t − 1`: прямую определяют две точки, квадратичный полином — три и так далее.

Каждый распределяет **собственный вклад**. Центрального участника, который сначала создал весь общий секрет, здесь нет. Это принципиальное отличие распределённой генерации ключа — DKG — от схемы «создать готовый ключ и затем разделить его».

Код: [`getRound3n4BroadcastMessages`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L190), [`VerifiableSS.share`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa/secret-sharing/vss.js#L27). Реализация ключей v2 импортирует этот модуль VSS из каталога предыдущей версии.

### 6. Секретные части передаются зашифрованными

Для пары участников вычисляется общий ECDH-секрет:

```text
u_A · Y_B = u_B · Y_A
```

На его основе код использует ECIES через библиотеку `eccrypto` для шифрования передаваемых частей. Сервер хранит и пересылает зашифрованные сообщения; по замыслу открытые секретные части ему не нужны.

Шифрование защищает от чтения, но публичные ключи участников также должны быть аутентифицированы. Если атакующий подменил ключ собеседника, сам факт шифрования проблему не решает.

Код: [`getRound3n4BroadcastMessages`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L190), [`encryption/ecies.js`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/encryption/ecies.js).

### 7. Каждый вычисляет итоговую долю

Участник складывает все части, адресованные ему:

```text
x_1 = f_A(1) + f_B(1) + f_C(1)
x_2 = f_A(2) + f_B(2) + f_C(2)
x_3 = f_A(3) + f_B(3) + f_C(3)
```

Получается общий полином:

```text
F(z) = f_A(z) + f_B(z) + f_C(z)
```

Его свободный коэффициент:

```text
x = F(0) = u_A + u_B + u_C
```

Это математический общий приватный ключ. Каждый знает свою точку `x_i = F(i)`, но не весь полином и не весь `x`.

Учебный пример по небольшому модулю 101, который не является параметром реального кошелька:

```text
F(z) = 60 + 31z

x_1 = 91
x_2 = 21
x_3 = 52

x = 2·x_1 − x_2 = 60 mod 101
```

Любые две доли позволяют восстановить секрет интерполяцией Лагранжа. В штатной работе кошелька целый ключ не восстанавливается: подпись вычисляется распределённо.

Код: [`calculateXi`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L269).

### 8. Проверка полученных частей

Для коэффициентов полиномов публикуются commitments — точки вида:

```text
C_k = a_k · G
```

Получатель должен проверить:

```text
f_i(j) · G = C_0 + j·C_1 + j²·C_2 + ...
```

Это verifiable secret sharing: проверка согласованности части с опубликованными обязательствами без раскрытия коэффициентов. В последнем раунде также используются доказательства знания дискретного логарифма.

**В данном коде ошибка VSS не останавливает выполнение.** Соответствующий дефект описан в разделе проблем реализации.

Код: [`verifyRound4Messages`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L228), [`validateShare`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa/secret-sharing/vss.js#L54).

### 9. Вычисление общего публичного ключа и адреса

```text
Y = Y_A + Y_B + Y_C
  = (u_A + u_B + u_C) · G
  = x · G
```

Знать `x`, чтобы вычислить `Y`, не требуется.

Из `Y` адаптер блокчейна получает адрес:

- Ethereum — обычный адрес EOA;
- Bitcoin в предоставленном адаптере — обычный P2PKH-адрес.

Создание такого кошелька не требует развёртывания multisig-контракта. Сам протокол генерации выполняется вне блокчейна. Порог и состав участников в адрес не записываются.

Код: [`calculatedY`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L283), [`TsWalletShard.resolveMultisigSession`](whcypher_app/src/serviceWorker/app/lib/TsWalletShard.ts#L180), [Ethereum-адаптер](chain-service/src/chain/eth.ts#L286), [Bitcoin-адаптер](chain-service/src/chain/btc.js#L282).

## Подписание транзакции

Участники выпускают одну подпись, а не собирают несколько обычных подписей под транзакцией.

1. Создаётся транзакция и вычисляется её хеш `h`.
2. Выбираются `t` участников.
3. Для выбранных номеров вычисляются коэффициенты Лагранжа `λ_i`.
4. Каждый использует взвешенную долю `ω_i = λ_i · x_i`.
5. Создаются свежие случайные значения для этой подписи.
6. Через Paillier и MtA участники вычисляют необходимые произведения секретных величин.
7. Формируются частичные результаты подписи.
8. Результаты объединяются в обычную подпись `(r, s)`.
9. Клиент проверяет её относительно общего публичного ключа и отправляет транзакцию.

Для обычной ECDSA:

```text
R = k · G
r = R.x mod q
s = k⁻¹ · (h + r·x) mod q
```

Здесь `k` — секретный одноразовый nonce подписи. Внутренние переменные MPC-протокола не следует автоматически отождествлять с `k` из этой формулы: распределённый алгоритм может хранить другое представление nonce, например его обратной величины.

Просто сложить обычные ECDSA-подписи нельзя: формула содержит обращение nonce и произведения секретов. Paillier позволяет выполнять необходимые гомоморфные вычисления, а MtA означает преобразование мультипликативного представления в аддитивное.

Финальный код нормализует `s` до low-S и вычисляет параметр восстановления публичного ключа.

Блокчейн проверяет обычную подпись относительно общего публичного ключа. Он не проверяет число участников и не читает `minimumSigAmount` из серверной базы данных. Порог должен обеспечиваться самим распределённым протоколом.

Код: [`SignatureSessionHandler`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/handlers/SignatureSessionHandler.ts#L60), [`protocol/signature.js`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/signature.js), [`mpc/mta.js`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/mpc/mta.js), [сборка итоговой подписи](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/signature.js#L415).

## Какие механизмы должны обеспечивать безопасность

| Механизм | Что обеспечивает | Чего сам по себе не обеспечивает |
| --- | --- | --- |
| Пороговые доли | Меньше `t` долей недостаточно для подписи в корректной схеме | Защиту при компрометации `t` участников |
| DKG | Отсутствие полного общего ключа у центрального генератора | Безопасность произвольно изменённого протокола |
| VSS и доказательства | Обнаружение некорректных действий участников | Корректность, если результат проверки игнорируется |
| Шифрование сообщений | Конфиденциальность передаваемых частей | Проверку личности получателя |
| Подписи API-запросов | Подтверждение владения ключом отправителя | Автоматическую защиту от повторного запроса |
| Шифрование хранилища | Защиту секретов на диске | Защиту, если пароль хранится рядом открытым |
| Проверка итоговой подписи | Корректность подписи под конкретным хешем | Соответствие транзакции намерению пользователя |

Корректная подпись может разрешать нежелательный перевод. Каждый подписант должен независимо проверять адрес, сумму, сеть, комиссии и содержимое вызова контракта.

Независимость участников также важна на уровне инфраструктуры: хранение нескольких долей на одном устройстве или под одним административным доступом позволяет одной компрометации преодолеть порог.

## Хранение секретов и восстановление

В локальное хранилище записываются:

- итоговая секретная доля `x_i`;
- секретные параметры собственного Paillier-ключа;
- путь деривации;
- общий публичный ключ и адрес;
- порог, номера и публичные данные участников;
- версия протокола.

`x_i` и параметры Paillier шифруются с использованием `u_i`, выводимого из seed. Сам seed хранится отдельно, зашифрованным пользовательским паролем. Предусмотрены серверные зашифрованные резервные копии; в настройках они включены по умолчанию.

**Для штатного восстановления одной seed-фразы недостаточно:** итоговая доля `x_i` зависит от случайных вкладов остальных участников. Нужна резервная копия состояния кошелька с итоговой долей и метаданными.

Практические последствия:

- seed без резервной копии доли не гарантирует восстановление;
- зашифрованная резервная копия без ключа расшифровки не возвращает доступ;
- если сохранилось минимум `t` исправных долей, средства остаются доступны;
- если осталось меньше `t` и нет способа восстановить остальные, доступ теряется;
- компрометация достаточного числа долей позволяет подписывать и математически восстановить общий секрет.

Код: [`WalletsDB.appendWalletShard`](whcypher_app/src/serviceWorker/db/WalletsDB.ts#L92), [`SeedsDB`](whcypher_app/src/serviceWorker/db/SeedsDB.ts), [`KeyManager`](whcypher_app/src/serviceWorker/app/models/KeyManager.ts), [резервное копирование](whcypher_app/src/serviceWorker/app/models/Wallet.ts#L897).

## Обнаруженные проблемы реализации

Следующие пункты относятся к исходному коммиту, указанному в начале документа. Добавление этого README не исправляет исходный код.

### 1. Ошибка VSS не останавливает генерацию

В `verifyRound4Messages`:

```js
if (!result) {
  new Error('VSS verification failed.')
}

return true
```

Пропущен `throw`. При отрицательном результате проверки метод всё равно возвращает успех.

Изолированная проверка подтвердила: при `validateShare = false` метод вернул `true` без исключения. Зависимости были подменены для проверки именно обработки результата, а не криптографической арифметики VSS.

Источник: [`protocol/keys.js`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L228).

### 2. Проверку корректности Paillier-ключа можно обойти

Проверяющая функция принимает специально сформированное доказательство с единичными элементами `zi`, которое не требует знания секретного ключа.

Изолированная проверка приняла такое доказательство даже для простого модуля `101`, который не является корректным модулем Paillier требуемого вида. Проверялся реальный код функции с независимыми минимальными реализациями SHA-256 и модульных операций.

Это подтверждает дефект проверяющей функции, но не является демонстрацией кражи средств через весь протокол. Наличие слова «proof» в структуре сообщения само по себе не означает, что нужное свойство доказано.

Источник: [`zkPillierCorrectKeyVerify`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/paillier/zk-paillier.js#L44).

### 3. Проверка длины Paillier-модулей сравнивает сами модули

В массив `bitLengths` добавляется `ek.n`, а не его битовая длина.

Три участника обычно создают три разных модуля одинаковой длины. Код видит три уникальных значения и отклоняет генерацию. Изолированная проверка на трёх различных 2048-битных значениях подтвердила исключение.

Для двух участников вычитание огромных десятичных строк также не является корректной проверкой длины: преобразование таких строк в `Number` теряет требуемую арифметику и может давать `NaN` при вычитании бесконечностей.

Источник: [`VaultSessionHandler`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/handlers/VaultSessionHandler.ts#L85).

### 4. Пароль и seed-фраза попадают в постоянное хранилище открытым текстом

Пароль разблокировки записывается в `application.password`, создаваемая и вводимая мнемоника — в `appInit`. Весь Redux подключён к `reduxed-chrome-storage` с `storageArea: 'local'`, без исключения этих полей.

На версии зависимости, закреплённой в lockfile (`8b74aaef38dfc97ae75d7db4b71472520ea80035`), проверено сохранение синтетического пароля и синтетических seed-слов в имитацию `chrome.storage.local`. Для проверки использовался поставляемый `dist/index.js` библиотеки.

Во время соответствующего состояния приложения рядом с зашифрованным seed оказывается информация для расшифровки. Мнемоника при создании также сохраняется до очистки состояния. При аварийном завершении нельзя полагаться на последующую очистку.

Источники: [`AccountsController.unlock`](whcypher_app/src/serviceWorker/app/controllers/AccountsController.ts#L122), [`applicationReducer`](whcypher_app/src/serviceWorker/app/store/reducers/applicationReducer.ts#L54), [`appInitReducer`](whcypher_app/src/serviceWorker/app/store/reducers/appInitReducer.ts), [`store.ts`](whcypher_app/src/serviceWorker/app/store/store.ts#L38), [`yarn.lock`](whcypher_app/yarn.lock#L24219).

### 5. Подписи API-запросов не обеспечивают полноценную защиту от replay

Сервер проверяет подписи тела и timestamp, но не проверяет свежесть timestamp и не учитывает одноразовый nonce.

Для запросов с телом в подписываемые данные не включаются HTTP-метод и URL. Привязка подписи к конкретному действию и сессии неполная.

Подписываемые данные должны однозначно связывать метод, путь, идентификатор сессии, тело, срок действия и одноразовый идентификатор. Сервер должен проверять срок и предотвращать повторное использование идентификатора.

Источник: [`post_request_signature_verifier.js`](whcypher_api/src/middleware/post_request_signature_verifier.js#L75).

### 6. Обработка повторных сообщений и присоединения ненадёжна

Сервер ищет дубликат по `state.roundName`, хотя поле называется `round`. Клиент часто ждёт строго определённое количество сообщений, поэтому повторы способны нарушить продвижение протокола.

Присоединение выполняется через последовательность «прочитать → проверить → добавить», без достаточных атомарных ограничений. В обработчике присоединения к генерации также нет проверки заполненности сессии перед добавлением участника.

Источники: [`vault_controller.js`](whcypher_api/src/controllers/vault_controller.js#L101), [`signature_controller.js`](whcypher_api/src/controllers/signature_controller.js#L216).

### 7. Модель полностью недоверенного сервера не обеспечена

Проверка подписей входящих запросов выполняется сервером. В ответе сессии генерации клиенту не передаются все необходимые подписи для независимой проверки происхождения сообщений.

В разобранном потоке также нет полноценной фиксации согласованного всеми состава участников и общего transcript — последовательности сообщений и параметров протокола. Поэтому утверждение «взлом сервера никак не влияет на безопасность» для этой реализации необоснованно.

Передача commitment и раскрытия одним сообщением дополнительно нарушает ожидаемое разделение фаз фиксации и раскрытия.

Источники: [проекция данных сессии](whcypher_api/src/controllers/vault_controller.js#L7), [`getRound1n2BroadcastMessage`](whcypher_app/src/serviceWorker/app/lib/threshold-ecdsa-v2/protocol/keys.js#L115).

### 8. Шифрование локального хранилища требует переработки

Используется строковый password-based API `CryptoJS.AES.encrypt(...)` без отдельной аутентификации ciphertext. У закреплённого CryptoJS 4.0.0 стандартный `EvpKDF` использует MD5 и одну итерацию, что плохо подходит для защиты человеческого пароля от перебора.

Для переработки нужны аутентифицированное шифрование, подходящий password KDF и исключение секретов из сохраняемого состояния. Шифрование случайным высокоэнтропийным секретом и шифрование пользовательским паролем имеют разные требования к защите от перебора.

Источники: [`SeedsDB._storeVault`](whcypher_app/src/serviceWorker/db/SeedsDB.ts#L249), [`WalletsDB`](whcypher_app/src/serviceWorker/db/WalletsDB.ts#L109), [CryptoJS 4.0.0 EvpKDF](https://raw.githubusercontent.com/brix/crypto-js/4.0.0/evpkdf.js), [CryptoJS 4.0.0 cipher-core](https://raw.githubusercontent.com/brix/crypto-js/4.0.0/cipher-core.js).

## Границы проверки

Выполнены чтение кода и изолированные проверки:

- обработка отрицательного результата VSS;
- отклонение трёх различных Paillier-модулей одинаковой битовой длины;
- принятие некорректного доказательства проверяющей функцией Paillier;
- сохранение синтетических секретов закреплённой библиотекой Redux-хранилища.

Полная система с браузером, MongoDB и блокчейнами не запускалась. Это не полный криптографический аудит и не подтверждение эксплуатации всей системы. Изолированные проверки выполнялись отдельно; они не добавлены в набор тестов репозитория.

## Вопросы для собеседования

| Вопрос | Ключевой ответ |
| --- | --- |
| 1. Где лежит общий приватный ключ? | Целиком штатно нигде. Есть распределённые доли и общий публичный ключ. |
| 2. Общий приватный ключ вообще существует? | Да, математически. Отсутствие его целиком в памяти не означает отсутствия как числа. |
| 3. Можно восстановить его из долей? | Да, `t` корректных Shamir-долей позволяют интерполировать секрет. Порог не запрещает сговор. |
| 4. Чем DKG отличается от «создать ключ и разрезать»? | При DKG нет центрального генератора, который изначально знает весь ключ. |
| 5. Почему недостаточно сложить публичные ключи? | Так получается общий ключ, но для произвольного `t` из `n` нужны распределение долей и соответствующий протокол подписи. |
| 6. Почему степень полинома `t−1`? | Его определяют `t` различных точек. |
| 7. Что такое VSS? | Разделение секрета с проверкой согласованности полученных частей. |
| 8. Чем `u_i` отличается от `x_i`? | `u_i` — исходный вклад участника; `x_i` — итоговая доля после взаимодействия со всеми. |
| 9. Кто должен быть онлайн при создании? | В этом коде все `n` участников. |
| 10. Кто должен быть онлайн при подписи? | Выбранные `t` участников; они проходят несколько раундов обмена. |
| 11. Получателю денег нужно участвовать? | Нет. Как при обычном переводе, достаточно его адреса. |
| 12. Есть ли комиссия за создание кошелька? | Сам протокол генерации выполняется вне блокчейна и не требует развёртывания контракта. |
| 13. Где блокчейн проверяет порог? | Нигде. Он проверяет одну ECDSA-подпись. Порог обеспечивается распределённым протоколом. |
| 14. Почему изменение `minimumSigAmount` на сервере не должно обходить защиту? | Порог заложен в распределение секретных долей, а не только в серверную проверку числа подтверждений. |
| 15. Чем это отличается от Safe или Bitcoin script multisig? | Там условие авторизации проверяется в блокчейне; здесь оно реализовано протоколом между подписантами. |
| 16. Видно ли число участников по адресу? | Сам адрес и обычная подпись не кодируют порог и состав участников. Серверные метаданные могут их раскрывать. |
| 17. Зачем нужен Paillier? | Для гомоморфных вычислений, необходимых при распределённом создании ECDSA-подписи. |
| 18. Можно просто сложить обычные ECDSA-подписи? | Нет. Формула содержит секретный nonce, его обращение и произведения секретов. |
| 19. Что делает интерполяция Лагранжа при подписи? | Позволяет выбранному подмножеству использовать взвешенные доли, соответствующие тому же общему секрету. |
| 20. Что произойдёт при повторном nonce подписи? | Возможна утечка приватного ключа. Нужно исключать повторное использование и откат состояния nonce. |
| 21. Чем nonce подписи отличается от nonce транзакции? | Первый — секретный одноразовый криптографический параметр; второй — публичный счётчик транзакций аккаунта. |
| 22. Можно возобновить прерванную подпись? | Только по правилам протокола. Нельзя произвольно повторять раунды или использовать одноразовые секреты для другого сообщения. |
| 23. Что если участник отправил мусор? | Проверки должны отклонить сообщение и безопасно прервать сессию. Это не обязательно позволяет завершить её с оставшимися. |
| 24. Что если участник отключился? | Создание может сорваться; для подписи можно начать новую сессию с другим допустимым набором, если хватает долей. |
| 25. Что даёт компрометация одной доли в «2 из 3»? | В корректной схеме её недостаточно для самостоятельной подписи. |
| 26. Что даёт компрометация двух долей? | Достаточные полномочия для подписи и возможность восстановления общего секрета. |
| 27. Можно все доли держать на одном компьютере? | Технически да, но одна компрометация устройства тогда может преодолеть весь порог. |
| 28. Защищает ли пароль от заражённого расширения? | Не во время работы с расшифрованными секретами. Пароль в основном защищает данные в состоянии покоя. |
| 29. Можно восстановить кошелёк только по seed? | В этой реализации штатно требуется также резервная копия итоговой доли и метаданных. |
| 30. Что произойдёт при потере участника? | Если осталось минимум `t` исправных долей, средства доступны. Иначе без предусмотренного восстановления доступ теряется. |
| 31. Можно поменять состав участников или порог? | Нужен отдельный протокол перераспределения долей либо новый кошелёк с переводом средств. Изменения записи БД недостаточно. |
| 32. Есть ли здесь готовый share refresh? | В разобранном потоке создания и подписи его нет. |
| 33. Чем refresh отличается от создания нового ключа? | Refresh обновляет доли с сохранением общего публичного ключа; новый ключ обычно означает новый адрес. |
| 34. Можно считать сервер безвредным ретранслятором? | Только при проверяемых клиентами подписях, составе участников, transcript и корректной модели протокола. Здесь есть пробелы. |
| 35. Почему HTTPS недостаточно? | Он защищает канал до сервера, но не от самого скомпрометированного сервера и не проверяет MPC-доказательства. |
| 36. Что подписывает пользователь: JSON или транзакцию? | API-запросы и блокчейн-транзакции имеют разные подписи и разные правила формирования хеша. Их нельзя смешивать. |
| 37. Как предотвратить подмену назначения перевода? | Каждый подписант должен самостоятельно разобрать подписываемую транзакцию и проверить её смысл. |
| 38. Как защищаться от повторов между EVM-сетями? | Привязывать транзакцию к сети через chain ID; для legacy-транзакций это описывает EIP-155. Это отдельная защита от replay API-запросов. |
| 39. Что такое low-S? | Нормализация `s`, устраняющая альтернативную форму ECDSA-подписи `(r, q−s)` там, где требуется каноничность. |
| 40. Значит ли валидная итоговая подпись, что MPC безопасен? | Нет. Протокол мог выдать правильную подпись и одновременно раскрыть секреты. |

## Как тестировать такой кошелёк

Кроме успешного перевода, нужны проверки:

- всех допустимых подмножеств подписантов для небольших `t` и `n`;
- отклонения неверных долей и доказательств;
- повторных, пропущенных и переставленных сообщений;
- подмены участника, номера, сети, версии протокола и транзакции;
- параллельных сессий и гонок присоединения;
- сбоя после каждого раунда, перезапуска и отката состояния;
- невозможности повторного использования nonce;
- восстановления из резервной копии;
- отсутствия seed, паролей и открытых долей в Redux, логах и незашифрованном хранилище;
- независимой проверки полученных подписей стандартной реализацией ECDSA.

Успешный сценарий не доказывает безопасность против злонамеренного участника. Нужны отрицательные сценарии, проверка связности всех доказательств с параметрами сессии и независимый анализ криптографического протокола.
